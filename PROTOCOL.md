# The protocol

This file is the executable form of the Benchmark Card in §3 of the paper. If a
reader disagrees with a specific choice below, the choice is named here so it can
be changed, and the effect of changing it can be measured.

Everything in this file is implemented in `experiments/protocol.py`. Nothing else
in the package defines a measurement.

---

## 1. Generators

| Item | Setting |
|:--|:--|
| Skeleton, main | Erdős–Rényi, `p = 2/(d−1)`, expected degree 2 |
| Skeleton, robustness | Barabási–Albert, preferential attachment, `m = 2` |
| Orientation | random topological order; `S[i, j] != 0` means `i → j` with `i < j` |
| Weights | `U([−1, −0.5] ∪ [0.5, 1])` |
| Mechanism family | linear-Gaussian; linear with exponential noise; non-linear (`tanh`) |
| Sample size | `n = 2d` (`5d` where stated) |
| Confounding | optional, a single latent variable affecting a fraction `q` of children |

The orientation convention matters and is fixed: a method that stores its
coefficients transposed scores worse, not differently. Both conventions are
scored and recorded (`f1` and `f1_flipped`), and Figure 1a uses the native one.

## 2. Solvers

| Name | What it is |
|:--|:--|
| `nt_official` | NOTEARS objective, Adam, **λ₁ = 0.1, ρ₀ = 1.0, ×10, 100 outer / 250 inner** |
| `nt_tuned` | Same, with λ₁ selected on held-out DAGs instead of inherited |
| `dagma` | The official DAGMA release, called unchanged |
| `cs_shipped` | The engine shipped by the toolkit measured in §4.4, called through its own API |
| `notears_official` | Faithful re-implementation of the published L-BFGS-B solver, used as a cross-check |

The NOTEARS objective is the one in Eq. (1):

```
min_W  0.5/n ‖X − XW‖²_F + λ₁‖W‖₁      s.t.  h(W) = tr(exp(W ∘ W)) − d = 0
```

`solver` names the optimisation; `λ₁`, `ρ₀`, `factor`, `outer` and `inner` are
recorded per row, because those are the quantities a reported "collapse"
conflates. The released `notears` package additionally symmetrises `W` and forces
non-negative weights; that is a quirk of that release rather than of the published
method, so it is not reproduced here, and the difference is stated in the paper.

## 3. Tuning budget

Every method — the baseline included — receives the same budget:

* the penalty is selected from `{0.003, 0.01, 0.03, 0.1, 0.3}`,
* on three **held-out** DAGs (seeds 1000–1002) that are disjoint from every test
  DAG,
* by mean structure F1 on those held-out DAGs.

No method selects a hyper-parameter on the test graph it is scored on. This is
the point on which the earlier submission's comparison failed: its NOTEARS column
came from a different generator, a different sample size and a different
threshold than the column it was compared against.

## 4. Scoring

| Item | Setting |
|:--|:--|
| Metric | structure F1 over the full `d × d` matrix, diagonal masked |
| Threshold | `τ = 0.3`, with a full τ-sweep reported alongside (`f1_oracle`, `tau_oracle`) |
| Direction | native and transposed, both recorded |
| Reported | mean ± SD over the seeds in the record file |

## 5. Identifiability boundary (§5)

Past `d ≈ 500` there is no ground-truth graph, only curated interaction networks
(STRING, TRRUST) that serve as undirected proxies. Two consequences are handled
explicitly:

* **A proxy supports edge existence only.** It is undirected, so no direction
  claim can be validated against it; it supplies precision without recall.
* **The right null is not the uniform one.** Restricting to the 500 genes with
  densest STRING coverage makes 66.9% of ordered pairs inside that subset already
  annotated (166,950 of 249,500). The enrichment reported by the earlier
  submission (8.4×) divided a subset-conditional numerator by a genome-wide
  denominator. Against the **matched** null the effect is 1.33×, with a net excess
  of 141 edges and one-sided binomial `p = 4.17e-38` — still significant, and
  still much smaller than reported.

The reproduction of those two figures is under `results/`; they are computed
once and quoted, not regenerated by `run_all.py`, because they depend on external
downloads.

## 6. Hardware

One NVIDIA RTX 5060 (8 GB), CUDA 12.8, PyTorch 2.11, Python 3.12, AMD Ryzen 9
